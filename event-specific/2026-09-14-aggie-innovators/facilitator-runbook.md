# Presenter runbook

## Before deck production

Speaking time (90 minutes), AI-Native Operating Framework, DeepSeek Harness preview, and gift eligibility/deadline are
confirmed. Finalize audience, scenario, biography examples, and remaining gift terms. Brad approves
the curriculum. Build slides from the storyboard only after these decisions are settled enough to
avoid needless rework.

## Rehearsal

- Check every requested tool on the presentation machine and record the actual version/model and local/cloud mode. Pre-download the chosen local Ollama model.
- Use fictional files and isolated demo surfaces. Verify baseline cannot retrieve framework files or prior project conversations.
- Rehearse Codex and Buzz twice: baseline and context-backed, then exception and fresh-session continuation. Preserve actual outputs and blank-to-completed rubric evidence.
- Confirm required integrations and permissions through supported configuration. If Buzz cannot consume the artifact directly, use a disclosed manual transfer; do not imply an integration exists.
- Time each segment. Preserve a recorded or screenshot fallback for every promised demo, labeled with tool/model/date and whether it was edited for time.
- Verify gift activation separately; an offer slide is not proof of membership entitlement.

## Day before

Recheck official tool docs, sign-ins, room connectivity, projector readability, notifications, and
gift terms. Rehearse without relying on the venue network for local artifacts. Verify the
presentation's exact links and QR targets.

## If something fails on stage

Give a failed request at most one short retry, then show the labeled rehearsal evidence. If only the
framework run succeeds because baseline infrastructure failed, do not score that as a framework
improvement. Record it as an availability problem. If both runs produce equally good work, show that
honestly and inspect continuation effort. If gift redemption is unavailable, state that setup is
pending and use a verified private follow-up route only after Brad chooses it.

## Visual verification once slides exist

Use the prior deck's HTML source and 16:9 design conventions. Verify keyboard navigation,
readability, overflow, links, and dark appearance on the presentation viewport. Produce PDF from one
1920×1080 screenshot per slide, preserving links; do not use browser print-to-PDF. Verify slide
count and page order. The built HTML and PDF have passed initial layout and parity checks; reverify after edits.

## After the event

Brad reviews attendee questions, actual demo evidence, and unredeemed gift support issues. Record
accepted lessons separately from suggestions; update reusable curriculum only through the program's
normal approval process. Publish only public-safe material with explicit authorization.
