What We Are Carrying Forward

Agents are useful because they combine context, tools, memory, and review.

LLM brain
Reasoning engine that needs clear context and boundaries.
Tools
Files, APIs, shell commands, search, calendars, tickets, docs, and other systems.
Memory
Markdown, task history, vector stores, repo files, and reusable project knowledge.
The risk is not theoretical
  • Shadow AI is already inside organizations.
  • Prompt injection changes how data can attack tools.
  • Agent credentials become new privileged identities.
  • Logs and review decide whether you can govern it.
The Shift

A chatbot answers. An agent team works a process.

Chatbot

Single-turn responses. Weak continuity. Good for quick drafting and explanation.

Agent

Goal-directed work. Tools, files, memory, steps, and reporting back.

Agent Team

Specialized roles working the same process from different angles.

If you can write an SOP for it, an agent can usually help map it, check it, draft it, or improve it.
Five Useful Roles

Do not ask one generic assistant to be the whole company.

Process Mapper

Turns messy work into steps, owners, inputs, outputs, decisions, and handoffs.

Security Reviewer

Finds sensitive data, access risks, compliance issues, approval gates, and audit needs.

Documentation Writer

Drafts SOPs, checklists, runbooks, templates, and explainers.

Implementation Planner

Breaks improvements into tasks, gates, rollback criteria, and next actions.

Automation Scout

Suggests safe automation opportunities ranked by impact, effort, and risk.

Human Orchestrator

Sets scope, approves sensitive work, verifies outputs, and owns the decision.

Why Markdown Matters

Plain text is the shared memory layer.

Markdown is readable by people, parseable by agents, renderable by GitHub, and easy to version.

  • Humans can inspect it.
  • Teams can version it.
  • Agents can reuse it.
  • Reviewers can audit it.
# Workflow Memory ## Goal Improve a low-risk process. ## Data Boundary Use sanitized examples only. ## Agent Team - Process Mapper - Security Reviewer - Documentation Writer ## Verification Human reviews before use.

Security Before Automation

Use sanitized examples. Treat output as draft work.

Do not paste
  • Passwords, keys, tokens, private keys
  • Customer, patient, employee, legal, or regulated records
  • Internal IPs, network diagrams, firewall rules
  • Unpatched vulnerabilities or production control details
Do instead
  • Use mock names and sanitized facts
  • Keep first workflows read-only or draft-only
  • Review every output before use
  • Keep humans in approval loops

Step 1

Create memory before asking for output.

The agent should start from stable context, not scattered chat fragments.

# InfraGard Demo Memory ## Workflow Field technicians collect site observations. A coordinator creates customer-safe summaries. ## Current Pain - inconsistent notes - missing data found late - slow reporting ## Data Boundary Use mock site names and mock measurements. No customer names, photos, locations, or regulated data.
Step 2

Good agents ask questions before they plan.

Read this Markdown memory. Before proposing a solution, ask me three clarifying questions that would help you map this workflow safely. Do not ask for secrets, customer data, regulated data, internal network details, or private operational details.
Scope

What exact output should this workflow produce?

Owners

Who captures, reviews, approves, and sends the report?

Boundary

Which data must stay out of the tool?

Step 3

Map the workflow before automating anything.

The first win is clarity: steps, owners, inputs, outputs, handoffs, and missing information.

Steps
Capture notes, review completeness, draft summary, approve, send.
Handoffs
Technician to coordinator to reviewer to customer contact.
Gaps
Missing measurements, unclear photos, undefined approval path.
Step 4

Guardrails come before automation.

Sensitive data

Customer names, exact site locations, photos, regulated records, and proprietary details stay out.

Access

The first version is draft-only. No direct system writes, no customer sends, no production control.

Approval

Human reviewer approves facts, safety language, and customer-ready wording.

Step 5

Turn the process into something people can use.

A practical artifact beats an impressive abstract answer.

Field report checklist
  • Site alias and date
  • Required measurements captured
  • Exceptions or missing data flagged
  • Reviewer approval recorded
  • Customer summary generated from approved facts
Step 6

The safest first experiment is usually draft-only.

First pilot

Use five sanitized historical examples. Generate summaries. Compare against human-written reports. Keep the agent out of production systems.

Stop conditions

Stop if the agent invents measurements, loses safety caveats, asks for sensitive data, or suggests bypassing review.

Measure success
Less missing data, faster draft turnaround, consistent customer wording, and fewer review corrections.
Step 7

Verification is part of the workflow.

Do not bolt it on later. Ask the agent to challenge its own output, then use human judgment.

Act as a skeptical reviewer. Identify: 1. factual assumptions, 2. missing edge cases, 3. unsafe recommendations, 4. human approval points, 5. tests or checks, 6. questions before production use.
What Good Looks Like

Useful agent output is specific, bounded, and reviewable.

Specific

Names the process, expected artifact, owners, inputs, outputs, and decision points.

Bounded

States what data stays out, what tools are allowed, and what requires approval.

Reviewable

Lists assumptions, verification steps, stop conditions, and unanswered questions.

Enterprise Guardrails

Four layers matter before broad rollout.

Policy
What the agent can and cannot do.
Access
Least privilege, scoped credentials, revocation, identity separation.
Observability
Logs, task IDs, actions, token usage, approvals, and review history.
Human intervention
Approval gates, stop conditions, and a fast circuit breaker.
Security Lens

Agents introduce new ways for data and tools to be abused.

Prompt injection

Malicious content inside data tells the agent to ignore instructions or leak information.

Data exposure

Overbroad read access can turn ordinary agent output into exfiltration.

Tool risk

Plugins, scripts, and integrations become supply-chain and privilege boundaries.

Agent identity

Shared human credentials make forensics and accountability weak.

Agent chaining

Agent-to-agent handoffs become new authorization decisions.

Runaway scope

"While I am at it" is scope creep, cost risk, and security risk.

Governed Rollout

Start small, add privilege slowly.

1. Personal literacy
Sanitized examples, local notes, no private data.
2. Draft-only internal workflow
SOPs, summaries, checklists, plans, evidence lists.
3. Read-only assisted workflow
Approved data sources, logging, reviewer sign-off.
4. Governed enterprise workflow
Identity, least privilege, audit, approvals, incident response, revocation.
Bad First Workflows

Some work should wait until governance exists.

External sends

Customer emails, legal notices, public posts, or regulatory statements without approval.

Production changes

Infrastructure changes, control actions, firewall updates, IAM edits, deployment changes.

Sensitive records

Patient, employee, legal, investigative, customer, or regulated data in unapproved tools.

After Today

One low-risk workflow in 30 days.

Week 1

Write the process in Markdown. Sanitize the example. Define data boundaries.

Week 2

Run Process Mapper and Security Reviewer. Capture clarifying questions.

Week 3

Draft one artifact: SOP, checklist, summary template, or implementation plan.

Week 4

Verify with a human reviewer. Decide keep, change, or stop.

Metric

Time saved, fewer missing fields, better consistency, fewer review corrections.

Stop condition

The agent asks for sensitive data, invents facts, bypasses approval, or expands scope.
